AI Development Framework

Turning agent speed into change you can actually approve.

A provider-agnostic operating model for AI-assisted delivery — where every gate is executable and no claim counts as evidence.

Talk deck AIDF v5.0.1 ~55 minutes

Who is talking

Prishan Fernando

I build delivery workflows for teams that ship with coding agents.

This framework is not theory. I built it, then used it to ship a real application end to end — and the parts that broke are why version 5 exists. Several slides in this deck are failures found that way.

Hands-on architect who'd rather build the thing than talk about it — 20+ years writing software, the last two obsessed with what AI-assisted delivery can responsibly become.

I care about this because safe AI implementation is not a feature, it's a prerequisite. Teams shipping fast without trust are just accelerating toward production chaos.

Opener: "Everyone here has had an agent hand them nine hundred lines that look right. This talk is about the hour after that."

Where we are

Agents made writing code cheap. They did not make trusting it cheap.

Implementation used to be the slow part. It isn't any more — so every queue behind it is now the constraint: review, testing, alignment, and the decision to release.

The whole argument, once

Same change, same agent, same diff. Two systems around it.

Nothing about the agent changed between those two lanes. The difference is entirely in what the repository refused to accept.

Observed, not imagined

Four places agent-built work goes wrong — and how each one hides.

The moment What it looks like at the time Why nobody catches it
Scope drifts A slightly larger problem than the one you asked about. The diff is coherent. Nothing in it is wrong — it just isn't what was approved.
Tests assert nothing Coverage rises. Everything passes. Written after the code, from the code. They pass against the bug too.
"Checks passed" A tidy pass/fail table in the PR body. A sentence an agent wrote looks identical to a result a runner produced.
UI arrives late It works. Then somebody finally sees it. First look lands after implementation, when changing it is expensive.

Every one of these passes a normal pipeline. That is the problem — not agent capability.

I

Act one

Process proportional to risk.

A typo and a schema migration should not cost the same to ship. Most frameworks fail here — by charging full ceremony for everything, until the team routes around all of it.

Classification

Two questions decide how much process a change earns.

The lifecycle

Eight steps forward. Five places a human decides. Three ways back.

Human control

Agents never approve their own work.

SpecA person owns the problem, the scope, the non-goals, and the track. Ambiguity is not authorization to build.
DesignFlow, states, and a clickable mockup — approved before planning starts, when changing direction is still cheap.
PlanFiles, approach, assumptions, and the test that will prove each acceptance criterion. No code until this is approved.
Pull requestAI review runs first and publishes findings; P0 and P1 are fixed or explicitly accepted. Then a human approves. Never the other way round.
SpecialistTrack C only. A named person accountable for the schema, the authorization model, or the infrastructure being changed.
ProductionRelease readiness, rollback path, and who is watching after the deploy.

The AI-review-before-human-approval ordering is deliberate. A reviewer who reads the machine's findings first asks better questions than one who reads the diff cold.

Command contracts

Eight prompt contracts, portable across any agent.

specIdea becomes classified intent. Picks the track, applies the risk tags.Human gate
designThrowaway runnable mockup, approved before any planning.Human gate
planApproved intent mapped onto real files, tests, and assumptions.Human gate
buildImplement only what was approved. Every new test must fail first.
validateRun the gates the track and tags require. Emit evidence.
previewThe real implementation, on an isolated surface, with controlled data.
reviewDiff, evidence, and risk. Findings ranked P0–P3 against file and line.Human gate
shipRelease notes and durable memory. Never merges or deploys by itself.Human gate

These are Markdown contracts, not tooling. The same eight work in Claude Code, Codex, Cursor, or a plain chat window — because none of them depend on a vendor feature.

Anatomy of a contract

Every contract answers the same four questions.

Do thisThe bounded job. build implements the approved plan and nothing adjacent to it.
Stop whenNamed conditions that end the turn: missing approval, scope growth, track escalation, three failures on one check.
A human ownsWhich decision is explicitly not the agent's to make.
Done meansA checklist specific enough to fail. Not "code is complete".
commands/build.md — completion criteria
- Plan approval confirmed before implementation began.
- Every new test fails against pre-change code.
- api: every changed endpoint is exercised
  through the real router, denied paths included;
  check-api-coverage.sh passes.
- ui: no raw colour, size, or spacing value
  outside the token layer.
- database: the data model document matches
  the schema as built.
- Track B/C: a changelog entry exists.
- No check result is asserted that a runner
  did not produce.

This one slide replaced eight in the previous version of this deck. If you have seen one contract, the shape of the other seven is predictable — which is the point of a contract.

Guardrails

Stopping with a clear question is a successful outcome.

No unapproved scope

Build refuses to start without an approved plan — and a design too, when the change touches UI.

No invented evidence

An agent never states that a check passed unless a runner produced that result.

No quiet escalation

Schema, authorization, secrets, or infrastructure reclassify the change upward and say so.

No irreversible act

Destructive commands, external messages, merges, and deploys all need explicit authorization.

The failure this prevents is specific. An agent that cannot stop will guess — and a plausible guess, written confidently, is far more expensive than a question.

II

Act two

Evidence, not confidence.

This is the load-bearing idea. Everything else in the framework is scaffolding around it.

The core confusion

"All tests passed" is a sentence. It is not a result.

Written in a PR body by a model optimising to sound finished, it is typographically identical to a result a runner produced. Reviewers cannot tell the difference — so the framework does not ask them to.

The corroboration rule

An agent may write evidence. It may not satisfy a gate.

The third lane is what stops this being theatre. Every real team needs a way past a gate; without an expiry, that way becomes the new default within a quarter.

Fail closed

A missing result is not a pass.

What a gate actually reads

The evidence artifact is boring on purpose.

evidence.json — emitted by every run, pass or fail
{
  "commit": "fe8ed83…",
  "runner": "ci",
  "classification": {
    "track": "B", "tags": ["api", "database"]
  },
  "checks": [
    { "name": "test",      "exit_code": 0 },
    { "name": "api-tests", "exit_code": 1 }
  ],
  "gates": [
    { "name": "test",        "status": "pass" },
    { "name": "api-tests",   "status": "fail" },
    { "name": "pr-approval", "status": "not_run" }
  ]
}

Why this shape

Exit codes, not adjectives. There is no field for how confident the agent felt. A process either returned zero or it did not.

A failed run is still evidence. The artifact is written either way. Suppressing it is how a framework ends up trusting prose.

Gates humans own are recorded as not_run — never quietly as passing. Automation cannot mark its own homework as reviewed.

A PR links this run. It does not restate the results in prose — because restating them is exactly where fabrication enters.

The testing rule

If a test passes before the fix, it is not testing the fix.

Mechanically checkable: stash the change, run the new test, confirm it fails, restore.

For a bug fix, the failing test is the reproduction. Writing it first is the only way to know you found the actual bug and not a plausible neighbour of it.

How agent-written tests fail

Asserts current behaviourDerived from the code, not the requirement. Passes through regressions.
Mocks the thing under testStill passes if you delete the implementation.
Tautologyexpect(result).toBeDefined()
Happy path onlyError and denied cases are where defects live.
Loosened assertionThe most dangerous edit, and the hardest to spot.

Authorization tests of the denied path are required for api and security. Broken access control is invisible to a suite that only ever tests an authorized user.

III

Act three

Where it earns its keep.

Four real gaps. Each one was found by building an application with this framework and then reading what it had actually produced — not by imagining what might go wrong.

Gap one

The API tag said "authorization tests". Every gate was green.

Without the gate

the rule was prose
  1. The agent adds a set of routes and writes tests for the pure helper functions those routes call.
  2. The tests are real, well-named, and pass. Coverage goes up.
  3. Not one of them makes an HTTP request. The router is never exercised.

Every endpoint ships uncovered, and the pipeline reports success.

With the gate

check-api-coverage.sh
  1. Routes are enumerated from the manifest and matched against test bodies.
  2. A test that names the endpoint but makes no request fails too — that is the loophole, closed.
  3. Unconfigured means failing, not skipping.

The build stops and names each uncovered endpoint.

The honest limit, stated in the standard: the check proves a test names and requests the endpoint. It cannot prove the test asserts anything meaningful. That is the reviewer's job — but the absent test is the failure that actually happened.

Gap two

One feature ended up with three visual languages.

The first UI change decides the palette, type scale, and spacing rhythm for every feature after it — whether anyone intends it to or not. The framework now makes that a decision instead of an accident.

Gap three

The architecture template claimed to cover the data model. It had none.

What the template actually asked for

## Data flow

Requests arrive at the API layer, which
validates input and delegates to the
service layer. The service layer owns
business rules and persists through the
repository.

…and that was the whole section.

Required whenever "a data model changes" — with nowhere to put a table, a column, a key, or a classification. The agent improvised an ERD anyway. That is luck, not a contract.

What it asks for now

## Data dictionary — transactions

column      type      null  class     …
──────────  ────────  ────  ────────
id          uuid      no    internal
user_id     uuid      no    pii
amount      numeric   no    sensitive
note        text      yes   pii

## Indexes — with the query each serves
## Authorization — rows a test can assert
## Retention and erasure path

Plus a crow's-foot ERD. An unclassified column defaults to sensitive — deliberately the inconvenient default, so leaving it blank costs more than filling it in.

Gap four

The green build that ships a data leak.

Happy-path coverage only

all tests pass
// the UI masks these fields…
function serialize(row) {
  return { ...row };  // …the API does not
}
  1. Every test authenticates as a user who is allowed to see the record.
  2. The response is asserted to contain the fields the UI shows.
  3. Nothing asserts what it must not contain.

Masked fields ship in the payload. Broken access control is invisible to this suite.

Denied paths required

api + security tags
  1. Unauthenticated, forbidden-per-object, not-found, and cross-tenant cases are each required, per endpoint.
  2. The test matrix records any case marked n/a — with the reason, visible to the reviewer.
  3. AI review reads the diff and the evidence before a human is asked to approve.

The cross-tenant test fails on the first run, naming the field.

The pattern underneath all four

A framework is judged by what happens on a bad day.

The moment What the framework does What happens without it
A spec is rejected Approval is recorded explicitly. Ambiguity is not authorization. The agent builds a plausible interpretation. Usually a larger one.
The track escalates mid-build Named assumptions make the violation recognisable. The agent stops. A schema change reaches production with no migration plan.
A gate fails Waivers need approver, reason, expiry, follow-up — and expire on their own. The gate is deleted or ignored. The exception becomes standard.
Review finds a P0 Review reads behaviour, not the summary. Findings anchor to file and line. The description is believed. It reads well and there is a lot to get through.

Three of those four are about stopping well. A framework that only describes the happy path has nothing to say on the days that matter.

IV

Act four

One product. Four kinds of change.

Everything so far has been the shape of the process. This act runs it four times on the same codebase — a feature, three flavours of bug, an architecture change, and a theme — and the four look nothing alike.

The case study

Beacon — a partner support portal.

Partners sign in, raise support cases, track status, and pull reports.

Nuxt front end, Nitro API under server/api, Postgres behind it. Four developers, two of whom drive agents for most of their output. GitFlow: main is production, develop is continuously deployed to QA, and every change gets its own worktree.

Beacon is a composite — the shape of several real products, not one of them. The four changes that follow are the four that actually arrive in a normal fortnight.

project.yaml — the parts that decide everything downstream
repository:
  integration_branch: develop
  production_branch: main
  qa_branch: develop

tags:
  enabled: [ui, api, database, security,
            infra, dependency, release, docs]
  preview_required_for: [ui, api, database]
  track_c_forced_by: [database, security,
            mcp-write, infra, release]

evidence:
  corroborating_runners: [ci]
  allow_local_runner: false

One file. Nobody argues about process again — they argue about the manifest, which is a much shorter argument and it happens once.

Change one — a feature

"Partners should be able to save a filter on the case list."

A feature is where the framework costs the most. It is also the only one of these four changes where every gate is obviously earned — which is why teams that only ever ship features conclude the process is heavy, and stop there.

Change two — a defect

The same bug costs three different amounts. Where you find it decides which.

Two rules hold across all three lanes. A regression test that fails against the unfixed code is never waived — without it, "fixed" is a claim. And an incident does not lower a track: a hotfix touching schema, authorization, or secrets is still Track C at three in the morning.

Change three — architecture

"Notifications should come off a queue instead of polling."

Change four — a UI design update

"New brand palette, and partners want a dark theme."

This is also where the framework subtracts a step. The mockup is skippable here — "a colour-token swap with no layout impact" is a reason the standard names — but only as a sentence written into the design doc, where the approver can read it and disagree. What is not skippable: contrast ratios re-measured for every semantic role, and UI QA exercising every state in both themes. Dark mode is precisely where contrast fails quietly.

The same eight contracts, four different weights

Proportion is the product. Everything else is plumbing.

The change Track and tags What it must produce What the framework refuses
Saved filters — a feature B · ui, api Design and mockup approved before planning; endpoint tests including denied paths; UI QA sign-off. A line of code before a human approved the plan.
A defect — dev, QA, or production A–C · origin picks the branch A regression test that fails against the unfixed code. An incident record when it reached users. "Fixed" with nothing that proves it was ever broken.
Polling → queue — architecture C · infra, dependency Named specialist, blast radius, rollback, an ADR, and the architecture document updated. A moved boundary reviewed as a refactor.
Palette and dark theme — design B · ui Contrast re-measured for every role; every screen exercised in both themes. A raw hex value living outside the token layer.

Nobody on this team negotiated any of that. The spec's two-line classification block selected it, the same way for all four — which is why the process survives the week everyone is busy.

V

Act five

Fitting it to a real repository.

A framework nobody can install is a blog post. This is the part that decides whether it survives contact with your codebase.

Gap five — the one you notice first

Adopting it used to mean seven framework folders in your project root.

Clone the framework

my-app/
├── adapters/
├── app/
├── commands/
├── docs/
├── guide/
├── reference/
├── schemas/
├── server/
├── standards/
├── templates/
└── project.yaml

red = framework   green = yours

Interleaved alphabetically, with nothing marking which is which. That is not a filing problem — it is a comprehension problem, for the humans reading the repo and for the agents deciding what is theirs to edit.

Run the installer

my-app/
├── .aidf/       ← the whole framework
├── app/
├── docs/
├── server/
├── AGENTS.md
├── CHANGELOG.md
└── project.yaml




.gitattributes marks .aidf/ vendored,
so upgrades stay out of your diffs.

One mental model, stated in the vendored README: .aidf/ is framework input, docs/ is project output. Everything else in the root belongs to you.

Parallel work

One agent, one worktree, one written contract.

Parallelism is only useful when ownership is crisp. A coordinator owns integration and conflict resolution — that role does not distribute.

Configure once

Nine tags. Each one adds evidence, never removes it.

TagApplies toAdditional evidence requiredForces
uiScreens, interaction, content flowApproved design and runnable mockup; UI foundation on the first one; Preview QA sign-offPreview
apiEndpoint, schema, or contract changeContract with a per-endpoint test matrix; HTTP-level tests including denied pathsPreview
databaseMigration, persistence, query shapeData model with ERD and dictionary; migration plan with seed profile; schema reviewTrack C
securityAuth, permissions, secrets, cryptoThreat model and a named security reviewTrack C
mcp-writeAgent-initiated mutationCapability review, audit plan, threat modelTrack C
dependencyAdded, removed, upgraded dependencyProvenance check, changelog review, vulnerability scan diffC at a trust boundary

Also infra, release, and docs. The taxonomy is defined in exactly one file — a consistency check fails the build if the manifest and the schema drift from it.

Live

Install it, then watch a gate refuse to pass.

  1. sh .aidf/reference/scripts/aidf-install.sh --target . — one directory, plus the docs tree and CI wiring
  2. sh .aidf/reference/scripts/validate-manifest.sh project.yaml — an empty required command is a failing gate
  3. sh .aidf/reference/scripts/run-gates.sh --track B --tags api — lint, test, build all pass…
  4. … and api-tests FAILS, naming every endpoint with no HTTP-level test
  5. cat evidence.json — runner=local, so it corroborates nothing. CI must re-run it.

Point to make while it runs: the gate that fails here is the one that was green for the same code before version 5. Nothing about the application changed.

Fallback if the demo will not run: skip to the appendix slide with the recorded output. Never narrate a result you did not just produce on screen.

Rollout

Adopt in slices. A grand rollout gets routed around.

FirstRun one real Track B feature all the way through: spec, plan, PR, review. Do not start with your hardest change.
Then stabiliseMake PR approval, branch protection, and CI evidence non-negotiable. Until branch protection is on, every gate is advisory — and advisory gates are decoration.
Then expandAdd the design gate and Preview where UI, API, or database risk actually justifies the cost.
Then one Track CExercise a migration or a permissions change deliberately, while everyone is still paying attention.
ContinuouslyReview friction in retro. A template nobody fills in honestly is worse than no template.

Is it working?

Five signals that tell you the truth.

SignalHealthyGoing wrong
Track mixTrack B is the default. Track C appears when there is real risk.Everything is Track A, or everything is Track C.
EvidencePRs link a CI run.PRs contain hand-written pass/fail tables again.
Approval timingSpecs, designs, and plans are approved before implementation starts.Approvals arrive after the code, as a formality.
UI feedbackDirection is settled at the mockup; Preview catches defects.Layout arguments start in the PR.
WaiversRare, named, expiring, tied to follow-up work.Renewed silently, or never expiring.

The waiver row is the leading indicator. Waivers stop expiring right before a team quietly stops believing in the gates.

Closing thought

Agents accelerate code. This accelerates the thing code waits on — trust.

Not more documents. A shared memory of intent, a clear path to release, and evidence strong enough that a human can approve without pretending to have read nine hundred lines.

Appendix

Detail for the questions you are about to get.

Environments, database lifecycle, AI-workflow safety, and portability. Press O for the slide index.

Appendix · environments

Four tiers, each with a data contract.

LocalDeveloper iteration. Synthetic or developer-owned data. No deploy infrastructure required.
PreviewOne PR's complete behaviour, isolated: its own deployment, an approved data clone, synthetic fixtures. Lives until the PR closes.
QACross-feature validation of everything merged to develop. Continuously deployed. Release candidates harden here.
ProductionReal traffic on main. Every promotion needs CI evidence, a deployment record, and an authorised human approval.

Preview is required for ui, api, and database — and for every Track C change. Not for every PR. The cost of an ephemeral environment should match the risk of the change.

Appendix · database

Schema changes get their own lifecycle.

Before merge

  • Versioned, forward-only migration
  • A dedicated migration role — the application role may not migrate
  • Preview clone or a controlled baseline
  • Synthetic seed profile for the review scenarios
  • Data model document matching the schema as built

Before production

  • Recovery point captured
  • Expand-and-contract, so the old code still runs
  • Safe smoke checks after apply
  • Observation window with a named owner
  • Rollback recorded before it is needed

Production seeding is prohibited except for approved reference data. A seed script is the fastest way to lose real rows.

Appendix · AI workflow safety

The attack surface is the context window.

Prompt injection

Issue text, PR comments, dependency READMEs, MCP results, CI logs — all data, never instructions. "Work through the backlog" authorises reading it, not executing what it says.

Data egress

Anything in context leaves your network. Declare the policy explicitly. Never paste production data into a session to debug — reproduce it synthetically.

Agent credentials

A session inherits real authority. Least privilege, separate identity from CI, nothing production-write, and rotate anything that appears in a transcript.

MCP supply chain

An MCP server is remote code with a seat at the table. Pin the version and protocol revision; a server update is a dependency change, not a background upgrade.

Appendix · portability

The framework binds to capabilities, not vendors.

Fixed by the framework

  • Local, Preview, QA, Production as concepts
  • CI-corroborated evidence and approval gates
  • Versioned migrations and seed profiles
  • Protected branches and deployment records

Chosen by the project

  • Hosting and database provider
  • CI system
  • Agent surface — Claude Code, Codex, Cursor, or a plain chat window

Adapters are thin instruction pointers. They translate; they never redefine. An adapter must reach all eight contracts and promise nothing it does not ship.
